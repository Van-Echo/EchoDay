# EchoDay 多 PC 互联测试指南

> 文档状态：待执行
> 编写日期：2026-09-09
> 对应阶段：[多端同步开发计划 S6](PLAN_Sync.md#s6windows-客户端与-tailscale)
> 当前原因：项目暂时没有第二台 Windows PC，实体 PC-PC 与三机收敛验收延期。

## 1. 测试目标

使用真实设备验证一个 EchoDay 同步组中的三台设备最终能够收敛：

- PC-A：唯一的 Windows 同步主机；
- PC-B：Windows 同步客户端；
- Phone-C：Android 同步客户端。

至少覆盖以下连接和故障场景：

1. 同一局域网内的附近主机发现与 PC-PC 配对；
2. 完整连接码和 `.echoday-pair` 配对文件；
3. Tailscale IP 异地连接；
4. MagicDNS 名称连接；
5. 三台设备分别新增、修改、完成和移动任务后的最终收敛；
6. 客户端离线编辑、主机休眠或重启、网络切换后的恢复；
7. 同字段并发修改产生冲突，以及不同字段并发修改自动合并；
8. 撤销设备后旧会话失效，重新加入必须再次配对。

本指南通过前，S6 只能标记为“功能已实现、实体多 PC 验收延期”，不能标记为完整关闭。

## 2. 设备与软件准备

### 2.1 设备

| 角色 | 最低要求 | 建议记录 |
| --- | --- | --- |
| PC-A 主机 | Windows 10/11 x64 | Windows 版本、设备名、网络类型 |
| PC-B 客户端 | Windows 10/11 x64 | Windows 版本、设备名、网络类型 |
| Phone-C 客户端 | Android 7.0 / API 24 或更高 | 型号、Android/API、CPU 架构 |

优先让 PC-A 与 PC-B 覆盖不同 Windows 版本；若只能使用相同版本，也要记录这一限制。

### 2.2 安装包

- 两台 PC 必须使用同一次构建产生的完整 Windows Release 目录，不能只复制 `EchoDay.exe`。
- Android 使用与 PC 协议版本一致的 APK。
- 正式便携包解压即用，不要求目标电脑安装 Flutter、Visual Studio 或 Android Studio。
- 测试前记录 EchoDay `versionName`、构建号、Git commit 和构建时间。

开发机生成 Windows Release：

```powershell
flutter build windows --release
```

产物目录：

```text
build/windows/x64/runner/Release/
```

### 2.3 测试数据与备份

1. 不使用唯一一份真实工作数据做破坏性测试。
2. 在三台设备上分别导出一份 JSON 备份，并记录保存位置。
3. PC-B 最好使用全新或可清空的测试数据。
4. 测试期间产生的任务统一使用 `MPSYNC-` 前缀，便于查找和清理。
5. 不在截图、Issue 或日志中公开完整连接码、邀请 token、完整证书指纹或私人 Tailnet 信息。

### 2.4 时间与网络

- 三台设备启用系统自动日期、时间和时区。
- PC-A 与 PC-B 首轮测试连接同一局域网。
- 三台设备均安装 Tailscale，并登录同一个 Tailnet。
- 记录 PC-A 的 Tailscale IPv4 和 MagicDNS 名称。
- 路由器若开启 AP/客户端隔离，附近发现和局域网直连会失败；这种环境应另换网络，不要把它误判为 EchoDay 故障。

在 PC-A 上检查 Tailscale：

```powershell
tailscale status
tailscale ip -4
```

在 PC-B 上验证主机端口；将地址和端口替换为 PC-A 设置页显示的值：

```powershell
Test-NetConnection -ComputerName <PC-A地址> -Port <EchoDay端口>
```

预期 `TcpTestSucceeded` 为 `True`。

## 3. 测试拓扑与角色约束

```text
                 ┌─────────────────────┐
                 │ PC-A / 同步主机     │
                 │ 保存设备与冲突状态  │
                 └─────────┬───────────┘
                           │ HTTPS + 指纹固定
                 ┌─────────┴───────────┐
                 │                     │
        ┌────────▼────────┐   ┌────────▼────────┐
        │ PC-B / 客户端   │   │ Phone-C / 客户端│
        │ 可完整离线编辑  │   │ 可完整离线编辑  │
        └─────────────────┘   └─────────────────┘
```

验收期间必须保持 PC-A 为唯一主机。不要把已有主机身份的数据库直接切换为客户端，也不要让 PC-B 创建第二个同步组冒充同一主机。

## 4. 基础预检

在开始配对前逐项确认：

- [ ] 三台设备的 EchoDay 版本一致；
- [ ] PC-A、PC-B 和 Phone-C 时间误差不超过一分钟；
- [ ] 三台设备都完成测试前 JSON 备份；
- [ ] PC-A 设置为“作为同步主机”；
- [ ] PC-A 设置页显示“正在运行”以及实际 HTTPS 地址；
- [ ] PC-B 设置为“连接到同步主机”；
- [ ] Phone-C 保持现有连接，或准备重新扫码加入；
- [ ] PC-A 的“已连接设备”中没有已撤销但名称相同的旧 PC-B；
- [ ] Windows 防火墙没有拦截 EchoDay 所选网络；
- [ ] 局域网或 Tailscale 的端口可达性测试通过。

如果任何一项失败，先停止正式用例并记录环境问题。

## 5. 用例 A：局域网附近发现与配对

### 操作步骤

1. 让 PC-A 与 PC-B 连接同一允许终端互访的局域网。
2. PC-A 打开“设置 → 多端同步”，选择局域网监听地址。
3. 确认主机状态为“正在运行”。
4. PC-A 点击“添加设备”，保持配对窗口打开。
5. PC-B 打开“设置 → 多端同步”，选择“连接到同步主机”。
6. PC-B 点击“发现附近主机”。
7. 选择 PC-A，点击“连接”。
8. 核对 PC-A 与 PC-B 显示的六位校验码完全一致。
9. 仅在校验码一致时，在 PC-A 点击“确认配对”。
10. 等待 PC-B 显示“已同步”。

### 预期结果

- [ ] 只有 PC-A 打开“添加设备”窗口时，PC-B 才能发现该邀请；
- [ ] 关闭窗口后，同一邀请不再通过附近发现出现；
- [ ] 双方六位校验码一致；
- [ ] PC-A 设备列表出现 PC-B，平台为 Windows；
- [ ] PC-B 显示 PC-A 名称、地址和上次同步时间；
- [ ] 首次同步后两台 PC 的 TODO、分类、标签和重复规则一致；
- [ ] 没有未处理冲突。

### 失败排查

- 未发现主机：确认配对窗口仍打开、两台 PC 同网段、路由器未启用客户端隔离，并检查 Windows 防火墙。
- 能发现但连接失败：在 PC-B 使用 `Test-NetConnection` 检查 PC-A 显示的 IP 和端口。
- 校验码不同：立即拒绝配对，关闭邀请并重新生成，不能继续。
- 邀请过期：主机重新点击“添加设备”，使用新的邀请。

## 6. 用例 B：完整连接码与配对文件

### 完整连接码

1. 在 PC-A 重新生成一次邀请。
2. 点击“复制”，通过用户信任的方式把完整连接码交给 PC-B。
3. PC-B 粘贴到“完整连接码”。
4. 如连接码中的地址在 PC-B 不可达，在“主机地址”中填入当前可达的局域网 IP、Tailscale IP 或 MagicDNS 名称。
5. 点击“连接”，核对六位校验码并在 PC-A 批准。

### 配对文件

1. PC-A 重新生成一次邀请，点击“导出配对文件”。
2. 保存 `.echoday-pair` 文件。
3. 将该文件通过用户信任的介质交给 PC-B。
4. PC-B 点击“导入配对文件”，选择文件并连接。
5. 核对六位校验码并在 PC-A 批准。
6. 等邀请过期后再次导入同一文件，确认应用拒绝过期邀请。

### 预期结果

- [ ] 连接码、二维码和配对文件使用同一套邀请与校验码；
- [ ] 配对文件不包含主机或客户端私钥；
- [ ] 成功使用或过期的邀请不能再次完成配对；
- [ ] 无效或损坏文件显示可读错误，不修改现有数据；
- [ ] 手动覆盖地址不会绕过 TLS 指纹检查。

## 7. 用例 C：三机基础收敛

确保 PC-B 与 Phone-C 均已加入 PC-A 的同一同步组，然后创建以下数据：

| 来源 | 任务标题 | 日期 | 额外字段 |
| --- | --- | --- | --- |
| PC-A | `MPSYNC-A-HOST` | 今天 +1 天 | 高优先级、分类 `MPSYNC` |
| PC-B | `MPSYNC-B-CLIENT` | 今天 +2 天 | 计划执行时间、标签 `PC-B` |
| Phone-C | `MPSYNC-C-PHONE` | 今天 +3 天 | DDL、备注 `Android source` |

按以下顺序操作：

1. PC-A 创建主机任务。
2. PC-B 创建客户端任务并点击“立即同步”。
3. Phone-C 创建手机任务，切到后台再回到 EchoDay。
4. PC-A 点击“主动同步全部设备”。
5. PC-B 点击“立即同步”。
6. Phone-C 点击“立即同步”。
7. 重复第 4～6 步，直至三台设备均显示没有新的上传或下载。

### 预期结果

- [ ] 三台设备都能找到三条测试任务；
- [ ] 日期、时间、DDL、优先级、分类、标签和备注一致；
- [ ] PC-A 只记录一个同步组和一个主机身份；
- [ ] PC-A 设备列表中 PC-B 与 Phone-C 均未撤销；
- [ ] 三台设备的冲突数均为 0。

## 8. 用例 D：双向修改、完成与跨日移动

1. PC-A 修改 `MPSYNC-B-CLIENT` 的备注。
2. PC-B 修改同一任务的计划执行时间。
3. Phone-C 将 `MPSYNC-A-HOST` 标记完成。
4. PC-B 把 `MPSYNC-C-PHONE` 拖到下一天。
5. 三台设备依次同步两轮。

预期不同字段组的修改可以自动合并：

- [ ] PC-A 的备注保留；
- [ ] PC-B 的计划执行时间保留；
- [ ] 完成状态在三端一致；
- [ ] 跨日移动后的所属日期在三端一致；
- [ ] 已完成任务保持删除线并位于底部。

## 9. 用例 E：并发冲突与恢复

1. 让 PC-B 与 Phone-C 暂时离线。
2. PC-A 把 `MPSYNC-A-HOST` 标题改为 `MPSYNC-A-HOST-A`。
3. PC-B 离线把同一标题改为 `MPSYNC-A-HOST-B`。
4. Phone-C 离线把同一标题改为 `MPSYNC-A-HOST-C`。
5. 依次恢复 PC-B、Phone-C 网络并同步。
6. 在 PC-A 查看“同步冲突”。
7. 记录最终胜出标题及失去的版本。
8. 选择一个失去的版本执行“恢复此版本”，再次让三端同步。

### 预期结果

- [ ] 系统确定性选择一个最终标题，不产生重复任务；
- [ ] 至少一个失去的同字段版本可在冲突入口查看；
- [ ] 恢复旧版本会生成新的同步变更并传播到三端；
- [ ] 冲突解决后未处理冲突数归零；
- [ ] 任一设备断网不阻塞其本地 TODO 编辑。

## 10. 用例 F：Tailscale IP 与异地网络

本用例必须避免两台 PC 仍通过同一局域网直连。建议让 PC-B 使用手机热点或另一条网络。

1. 保持三台设备登录同一 Tailnet。
2. PC-A 在同步设置中选择 Tailscale IPv4 监听地址并重启服务。
3. PC-B 在已连接信息中把主机地址改为 PC-A 的 Tailscale IPv4。
4. 点击“保存并重试”。
5. 使用 `Test-NetConnection` 再次确认端口可达。
6. 在 PC-B 创建 `MPSYNC-TAIL-IP` 并同步。
7. Phone-C 打开 EchoDay 并同步。

### 预期结果

- [ ] PC-B 在异地网络下显示“已同步”；
- [ ] `MPSYNC-TAIL-IP` 出现在 PC-A 与 Phone-C；
- [ ] EchoDay 没有要求项目方账号或云服务器；
- [ ] Tailscale 断开时显示主机不可达，但本地编辑仍可用；
- [ ] Tailscale 恢复后点击“立即同步”即可收敛。

## 11. 用例 G：MagicDNS

1. 在 Tailscale 管理端确认 MagicDNS 已启用。
2. 在 PC-B 上先解析或 ping PC-A 的 MagicDNS 名称。
3. 将 EchoDay 客户端主机地址改为该 MagicDNS 名称，不带 `https://`、路径或端口。
4. 端口单独填写 PC-A 当前 EchoDay 端口。
5. 点击“保存并重试”。
6. 创建 `MPSYNC-MAGICDNS` 并同步到三端。

### 预期结果

- [ ] MagicDNS 名称可以保存并连接；
- [ ] TLS 指纹仍与初次配对固定的主机一致；
- [ ] 名称解析失败时显示主机不可达，不清除本地任务；
- [ ] 恢复解析后无需重新配对即可同步。

## 12. 用例 H：休眠、重启与网络切换

依次执行，每一步都创建一个唯一任务并确认最终传播：

1. PC-A 休眠，PC-B 离线新增 `MPSYNC-HOST-SLEEP`；唤醒 PC-A 后同步。
2. 完全退出 PC-A EchoDay，PC-B 新增 `MPSYNC-HOST-EXIT`；重新启动主机后同步。
3. 重启 PC-A，确认主机模式自动恢复且端口重新监听。
4. PC-B 从局域网切到 Tailscale，修改地址并重试。
5. PC-B 在同步进行中新增另一个任务，确认该变更不会丢失，下一轮可以上传。
6. Phone-C 在 PC-A 关闭时离线编辑，主机恢复后打开手机完成同步。

### 预期结果

- [ ] 主机离线期间所有客户端仍可编辑；
- [ ] 主机恢复后不要求清空数据库或重新安装；
- [ ] 网络切换不会改变同步组身份；
- [ ] 同步期间产生的新变更留在队列中；
- [ ] 最终三端收敛且无数据丢失。

## 13. 用例 I：设备备注、主动同步与撤销

1. PC-A 给 PC-B 添加备注 `备用 Windows 客户端`。
2. PC-A 对 PC-B 发起单设备同步请求。
3. PC-B 下次连接后确认完成同步。
4. PC-A 对所有设备发起同步请求。
5. PC-A 撤销 PC-B。
6. PC-B 点击“立即同步”。
7. PC-B 解除本机连接后，使用新邀请重新配对。

### 预期结果

- [ ] 备注重启 PC-A 后仍保留；
- [ ] 在线设备响应主动同步，离线设备显示等待下次连接；
- [ ] 撤销后 PC-B 的旧会话立即失效；
- [ ] PC-B 本地 TODO 不因撤销或解除连接而删除；
- [ ] 重新加入必须重新核对六位校验码并由主机批准。

## 14. 数据一致性核对

测试结束后，在三端分别核对：

- TODO 数量以及每条 `MPSYNC-` 任务；
- 完成状态、所属日期、执行时间、DDL 和备注；
- 分类、标签及颜色；
- 重复任务系列与例外；
- 未处理冲突数量；
- 最后同步时间和本次上传/下载数量；
- PC-A 的设备列表、备注和撤销状态。

可以从三端分别导出 JSON 用于人工比对业务数据，但不能要求整个文件字节完全相同：导出时间与设备本地设置可能不同。重点比较 TODO、分类、标签和重复规则。

## 15. 通过标准

以下条件必须全部满足：

- [ ] PC-A、PC-B、Phone-C 可以加入同一同步组；
- [ ] PC-A 始终是唯一主机；
- [ ] 局域网真实设备同步通过；
- [ ] Tailscale 异地真实设备同步通过；
- [ ] MagicDNS 通过，或明确记录为环境不支持且 Tailscale IP 仍通过；
- [ ] 三端新增、编辑、完成、删除、跨日移动最终一致；
- [ ] 离线与主机重启期间没有数据丢失；
- [ ] 同字段冲突可见、可恢复、可再次传播；
- [ ] 撤销设备后旧会话不可继续同步；
- [ ] 没有崩溃、数据库损坏或持续重复同步；
- [ ] 所有失败提示可读，不暴露私钥或完整 token；
- [ ] 测试前备份可以正常预检和恢复。

任何阻断级数据丢失、安全绕过、无法收敛或数据库损坏都判定整轮失败。

## 18. 收尾

1. 三端各执行一次“立即同步”，确认上传和下载归零。
2. 导出测试后备份。
3. 删除全部 `MPSYNC-` 测试任务，并再次同步，确认删除传播到三端。
4. 若 PC-B 不再作为客户端，在 PC-A 撤销设备，并在 PC-B 安全解除连接。
5. 保存测试记录与必要的脱敏证据。
