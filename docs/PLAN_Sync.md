> 计划状态：执行中（S0～S5、S7 已完成；S6 功能已实现但实体多 PC 验收延期；下一阶段为 S8）
> 制定日期：2026-09-09
> 目标版本：V1.0.1
> 现有基线：Windows / Android v0.1.0，Flutter 3.47.2 / Dart 3.13.2
> 关联文档：[产品需求文档](PRD.md) · [Windows 开发计划](PLAN.md) · [Android 开发计划](PLAN_Android.md) · [同步协议 V1](SYNC_PROTOCOL_V1.md) · [Schema v3](SYNC_SCHEMA_V3.md) · [安全基线](SYNC_SECURITY.md)

## 1. 目标

为 EchoDay 增加不依赖项目方云服务器的多端数据互通能力：

- 一台 Windows PC 作为同步组内唯一的“同步主机”。
- 其他 Windows PC 与 Android 设备作为客户端。
- 同一局域网内直接连接；跨互联网时复用用户已有的 Tailscale 网络。
- EchoDay 不接入 Tailscale SDK、不代管 Tailscale 账号，也不承担中继服务成本。
- 所有设备仍然以本地数据库为工作基础；主机不可用时可以继续离线编辑。
- 再次连接后进行双向增量同步，并以确定、可恢复的规则处理冲突。
- Android 只在打开应用、回到应用前台以及用户点击手动同步时发起同步，不常驻后台。
- Windows 主机提供设备管理、备注、主动同步和同步状态展示。
- Windows 用户可以自定义默认备份目录和备份保留数量。

本阶段完成并通过发布验收后，应用版本提升至 **V1.0.1**。

## 2. 已确认的产品决策

以下决策已经锁定，开发过程中不再反复讨论：

1. 一个同步组只能有一台主 PC。
2. Android 和其他 PC 都是客户端，不承担中继职责。
3. 局域网同步为内建能力；Tailscale 只负责提供设备间可达的私有网络。
4. Android 不使用 WorkManager 周期轮询、常驻前台服务或 FCM 推送。
5. Android 自动同步时机只有：
   - 冷启动并进入 EchoDay；
   - 从后台回到 EchoDay；
   - 用户点击“立即同步”。
6. PC 主机启动或从休眠恢复后启动服务，但无法唤醒已被 Android 系统挂起的客户端；客户端下次进入 EchoDay 时完成同步。
7. PC-PC 配对不要求手机中转，使用局域网发现、连接码、主机地址或临时配对文件。
8. 同步功能是同一应用中的可选能力，不制作独立的“Server 版”安装包。
9. 关闭同步服务不会切换数据库，也不会影响离线编辑。
10. V1.0.1 不提供项目方托管的云服务、账号体系或公网中继。

## 3. 非目标

以下能力不属于 V1.0.1：

- EchoDay 官方账号与云空间。
- 官方 TURN、信令、推送或中继服务器。
- 多台主 PC 组成的网状同步网络。
- 多人同时协作编辑同一个日历。
- Android 应用关闭后的实时推送和强制唤醒。
- 自动修改路由器 UPnP、NAT-PMP 或公网端口映射。
- 把未加密的 EchoDay HTTP 服务直接暴露到公网。
- WebDAV、S3、OneDrive 等异步存储后端的正式交付。

同步传输层必须预留扩展接口，未来可以增加用户自备 WebDAV 等异步后端，但不会阻塞 V1.0.1。

## 4. 产品模型

### 4.1 角色

#### 同步主机

- 仅支持 Windows。
- 保存同步组的完整数据副本和设备注册表。
- 接收客户端增量、执行合并，再向客户端返回缺失增量。
- 管理设备备注、撤销状态、最后同步时间和待处理冲突。
- 可以主动通知当前保持连接的客户端开始同步。
- 对离线客户端只记录“等待同步”，不宣称已完成。

#### 同步客户端

- 支持 Windows 与 Android。
- 始终保存自己的完整本地数据副本。
- 离线时正常新增、编辑、完成、删除和排序任务。
- 连接主机后先推送本地增量，再拉取主机增量，直至双方游标稳定。
- 不监听公网端口，不接受其他客户端直连。

### 4.2 单主机约束

- 每个同步组生成唯一 `syncGroupId`。
- 组内唯一角色为 `host` 的设备由 `hostDeviceId` 标识。
- 普通客户端不能自行升级为主机。
- 主机迁移不在首轮普通交互中提供；如确需迁移，必须通过完整备份、解除原同步组并重新配对完成。
- 主机数据库不是唯一数据存储，但它是同步顺序、设备成员和冲突记录的协调中心。

### 4.3 同步开关

PC 设置中的模式为：

- `关闭同步`
- `作为同步主机`
- `连接到同步主机`

模式变化只启动或停止同步组件，不能清空或替换现有数据库。切换角色前必须显示影响说明，并自动创建安全备份。

## 5. 网络与连接

### 5.1 局域网

- 主机通过安全 HTTP 服务监听用户允许的私有网络接口。
- 默认使用动态高位端口，实际端口保存在设备本地设置中。
- V1 的 Windows 附近主机发现使用限时 UDP 邀请广播：只有主机正在展示“添加设备”窗口时才广播完整的一次性邀请，关闭窗口或邀请过期后立即停止。
- Android 继续以扫码为主要入口，不在后台持续扫描局域网。
- 局域网发现失败时仍可粘贴完整连接码、手动覆盖主机地址或导入临时配对文件；后续如增加 DNS-SD/mDNS，只替换发现层，不改变配对协议。
- 不在公共网络配置文件上默认放行 Windows 防火墙。

### 5.2 Tailscale

- EchoDay 只把 Tailscale 地址视作另一条可用网络接口。
- 主机界面列出可用的局域网地址和 Tailscale 地址，由用户选择二维码中使用的地址。
- 支持 Tailscale IP、MagicDNS 主机名和手动地址。
- 不读取用户的 Tailscale 账号、Tailnet 成员或访问控制配置。
- Tailscale 不可用时，不影响局域网和纯离线功能。
- 配对认证仍由 EchoDay 自己完成，不能仅凭“处于同一 Tailnet”自动信任设备。

### 5.3 连接状态

统一状态枚举：

- `关闭`
- `等待连接`
- `正在连接`
- `正在同步`
- `已同步`
- `有待同步更改`
- `设备离线`
- `需要处理冲突`
- `认证失败`
- `协议不兼容`
- `网络错误`

所有错误必须可读，不直接向普通用户展示 Socket 堆栈或数据库异常。

## 6. 配对设计

### 6.1 设备身份

每台设备首次启用同步时生成：

- 永久 `deviceId`；
- 设备公私钥对；
- 用户可修改的设备名称；
- 平台、应用版本和同步协议版本；
- 本地逻辑时钟状态。

私钥通过 `DeviceSecretStore` 抽象保存：

- Android 使用系统 Keystore 支持的安全存储；
- Windows 使用 DPAPI、Windows Credential Manager 或经安全评审的等效实现；
- 私钥、长期令牌和配对凭据不得进入 JSON 备份、日志、Crash 信息或同步负载。

### 6.2 二维码

二维码使用版本化 URI，例如：

```text
echoday://pair?v=1&host=<address>&port=<port>&group=<id>&fingerprint=<key>&token=<one-time-token>
```

要求：

- 一次性令牌至少 128 bit 随机熵；
- 默认 5 分钟过期；
- 成功或失败达到限制次数后立即失效；
- 二维码不包含长期私钥或可重复使用的主机密码；
- Android 扫码后显示主机名和六位校验码；
- PC 主机必须人工确认设备名与校验码后才完成配对。

### 6.3 PC-PC 配对

Windows 客户端依次提供：

1. “发现附近主机”；
2. “输入连接码”；
3. “输入主机地址”；
4. “导入 `.echoday-pair` 临时配对文件”。

连接码和配对文件与二维码使用同一套一次性邀请记录，不增加第二套身份机制。临时配对文件成功使用或过期后失效。

### 6.4 解除连接

- 主机撤销设备后，将其公钥加入撤销记录并关闭现有会话。
- 客户端解除连接后保留本地 TODO 数据，但清除同步组凭据和游标。
- 被撤销设备再次连接必须重新配对。
- 设备被撤销后不再阻塞墓碑和日志的安全清理。

- 分类；
- 标签；
- TODO 与标签的关系；
- 重复任务系列；
- 重复任务例外。

### 7.2 不同步的数据

- 默认备份目录和备份保留策略；
- 同步主机开关、监听地址和端口；

V1.0.1 默认不跨设备同步 `settings` 表。未来如需同步语言、主题等偏好，必须先建立明确的“可漫游设置白名单”。

## 8. 数据库升级与同步日志

### 8.1 Schema 升级

当前数据库 schema v2 已为主要实体提供 UUID、`updatedAt`、`deletedAt` 和 `revision` 基线，但这些字段不足以单独解决多设备并发。

同步开发将数据库升级至新的版本，具体版本号以实施时最新 schema 为准，并新增：

- `sync_groups`
- `sync_devices`
- `sync_pairing_invites`
- `sync_changes`
- `sync_entity_versions`
- `sync_relation_dots`
- `sync_cursors`
- `sync_conflicts`
- `sync_runtime_state`

必须生成并提交 Drift schema 快照，提供从所有公开版本数据库到新版本的迁移测试。

### 8.2 变更日志

每个本地写操作必须在同一数据库事务中：

1. 修改业务实体；
2. 增加实体版本；
3. 写入一条或多条 `sync_changes`；
4. 提交事务。

一条变更至少包含：

- 全局唯一 `operationId`；
- `syncGroupId`；
- `sourceDeviceId`；
- 设备内单调递增 `sequence`；
- `transactionId`；
- `entityType` 与 `entityId`；
- `operationType`；
- 字段组；
- 版本化 JSON payload；
- 混合逻辑时钟；
- 创建时间。

远端变更应用时必须标记来源，不能再次作为新的本地操作回写，从而避免同步回声。

### 8.3 TODO 标签关系

现有 `todo_tags` 只有联合主键，没有更新时间与软删除状态。同步实现不得仅比较当前集合，应采用可合并的关系操作：

- 标签添加产生唯一 add operation；
- 标签移除引用已经观察到的 add operation；
- 同步后可以确定性地计算当前标签集合；
- 删除 TODO 或标签时同步生成对应关系墓碑。

### 8.4 删除墓碑

- 删除操作不能立即物理清除。
- 主机必须知道哪些有效客户端已确认该删除。
- 所有未撤销设备确认后，墓碑仍保留一个安全窗口再压缩。
- 长期离线设备会阻止清理；用户撤销该设备后可以解除阻塞。
- 客户端拿到的新快照必须包含尚未安全清理的墓碑基线。

## 9. 版本、时钟与冲突

### 9.1 混合逻辑时钟

不能只使用设备系统时间决定胜负。手机或 PC 时间错误时，纯 `updatedAt` 会错误覆盖数据。

采用因果游标判断先后与并发，再使用由以下内容组成的可比较版本：

- 物理 UTC 毫秒；
- 逻辑计数器；
- `deviceId` 作为最终稳定决胜项。

每条操作携带“设备 ID → 已观察连续 sequence”的因果游标。因果后继永远覆盖前驱；只有互相未观察到的操作才是并发。接收远端操作时推进本地逻辑时钟，保证相同输入在所有设备上得到相同顺序。

### 9.2 字段分组

TODO 至少拆分为以下同步字段组，避免无关修改互相覆盖：

- `content`：标题、日期、执行时间、DDL、优先级、分类、备注和重复关联；
- `completion`：完成状态与完成时间；
- `order`：手动排序值；
- `tags`：标签关系操作；
- `deletion`：删除与恢复状态。

### 9.3 冲突规则

- 不同实体直接合并。
- 同一实体不同字段组分别合并。
- 同一字段组只有一端变更时直接采用变更。
- 同一字段组并发变更时使用混合逻辑时钟确定当前值，同时把失去的版本写入 `sync_conflicts`。
- 删除与编辑并发时默认保留删除结果，并把编辑版本放入冲突记录，允许用户恢复为新任务。
- 冲突处理必须可撤销，不能静默丢弃用户文本。
- 重复规则及例外必须作为一个经过约束校验的事务应用，避免出现无主例外。

## 10. 同步协议

### 10.1 协议原则

- 所有消息包含 `protocolVersion`。
- 使用 JSON 作为首版交换格式，保持可调试性和开源可读性。
- 大负载启用 gzip；服务端限制解压后大小、单批操作数和字段长度。
- 每个请求带设备身份、会话信息、时间窗口和防重放数据。
- 所有写入幂等；重复收到相同 `operationId` 不得重复修改数据库。
- 不兼容的协议或 schema 必须在写数据库前拒绝。

### 10.2 建议端点

```text
GET  /sync/v1/info
POST /sync/v1/pair/start
POST /sync/v1/pair/confirm
POST /sync/v1/session
POST /sync/v1/push
POST /sync/v1/pull
POST /sync/v1/ack
GET  /sync/v1/snapshot
GET  /sync/v1/events
```

具体路由可在实现阶段调整，但协议 DTO、错误码和兼容规则必须独立于页面与 `HttpServer`。

### 10.3 单次同步顺序

```text
建立加密会话
  → 校验设备与协议
  → 客户端推送主机尚未确认的本地增量
  → 主机事务性应用并返回确认游标
  → 客户端按自己的游标拉取主机增量
  → 客户端事务性应用并确认
  → 双方再次比较摘要
  → 游标一致后标记同步完成
```

连接中断后从已确认游标继续，不重新覆盖整库。

### 10.4 初次同步

配对前必须检测客户端是否已有用户数据：

- 空客户端：先创建安全备份，再接收主机完整快照。
- 非空客户端：展示双方记录数量与时间，默认执行双向合并。
- 用户可以选择“仅保留主机数据”，但必须二次确认并先备份客户端数据。
- 不提供客户端无确认覆盖主机的快捷选项。
- 首次合并完成后再建立正式游标基线。

## 11. 安全设计

### 11.1 传输安全

- 主机使用 TLS 或经过安全评审的等效加密会话。
- 客户端通过二维码或连接码固定主机公钥指纹，不依赖公共 CA 识别家庭设备。
- 配对后进行双向设备认证。
- 会话密钥定期轮换，长期凭据不得直接作为每次请求的明文令牌。

### 11.2 服务暴露

- 默认仅监听用户明确选择的私有接口。
- 设置页明确显示当前监听地址和端口。
- 关闭主机模式后必须立即关闭监听 Socket。
- 解除最后一个客户端不会自动开放匿名配对。
- 配对入口默认关闭，只在用户点击“添加设备”后短时开启。
- 不自动创建公网端口映射。

### 11.3 输入防护

- 限制二维码、连接码、请求体、批次、JSON 深度和字符串长度。
- 所有同步 payload 复用并扩展备份格式的字段与引用校验。
- 数据库应用使用事务和外键约束。
- 拒绝路径字段、可执行内容和未知实体类型。
- 日志隐藏令牌、私钥、完整任务正文和用户网络地址。

## 12. 现有备份能力的复用边界

现有 `LocalBackupRepository` 可以复用：

- UTC JSON 序列化；
- 数据表快照；
- 格式版本；
- 字段、ID、时间与引用关系校验；
- 事务性恢复；
- 安全备份文件命名。

但不能直接以反复“导出整库 → 合并导入”实现同步，原因包括：

- 现有合并策略遇到相同 ID 会跳过，不能更新已存在记录；
- 完整快照无法高效表示增量与确认游标；
- 无法表达两个设备对同一字段的并发修改；
- 无法确定删除是否已被所有设备观察；
- 当前备份包含设置，而同步必须排除设备本地设置。

实施时应抽取共享的 `BackupCodec` / `EntityCodec` / `DataValidator`，供备份和同步分别使用。备份保持面向文件的完整快照；同步使用增量操作协议。

## 13. 默认备份目录

### 13.1 设置项

Windows“数据备份与恢复”增加：

- 默认备份目录；
- “选择目录”；
- “打开目录”；
- “测试写入”；
- 自动备份开关；
- 最大保留份数；
- 当前目录不可用时的状态提示。

默认备份目录属于设备本地设置，不进入同步。

### 13.2 备份触发

- 每次数据库 schema 升级前；
- 首次加入同步组前；
- 更换主机/客户端角色前；
- 首次完整同步或覆盖本地数据前；
- 用户执行覆盖恢复或清空数据前；
- 每个自然日首次成功同步前最多自动备份一次；
- 用户手动点击“立即备份”。

普通增量同步不为每一批操作生成完整 JSON。

### 13.3 目录与保留策略

- 用户目录下建立 `EchoDay Backups` 和 `Safety Backups` 子目录，或使用清晰的文件名前缀。
- 默认最多保留 10 份自动日常备份，安全备份单独计数。
- 删除旧自动备份前校验目标位于用户已选择的备份目录内。
- 不自动删除用户手动导出的文件。
- 自定义目录失效时回退到应用支持目录，并在设置页持续显示警告。
- 修改备份目录不移动正在使用的 SQLite 数据库。

## 14. 设置与交互

### 14.1 Windows 主机

设置页新增可折叠的“多端同步”栏目：

- 模式选择；
- 服务启停状态；
- 随 EchoDay 启动；
- 随 Windows 启动；
- 最小化到托盘后继续服务；
- 网络接口和地址选择；
- 生成二维码/连接码；
- 已连接设备列表；
- 设备名称、备注、平台和应用版本；
- 在线状态、最后同步时间、待同步数量；
- 单设备“立即同步”“修改备注”“解除连接”；
- “主动同步所有可达设备”；
- 冲突入口与错误详情。

“主动同步所有可达设备”必须返回逐设备结果，例如“2 台成功、1 台离线、1 台需要升级”，不能把离线设备算作整体失败。

### 14.2 Windows 客户端

- 发现附近主机；
- 输入连接码/地址；
- 导入临时配对文件；
- 显示当前主机、最后同步时间和待同步数量；
- “立即同步”；
- “解除连接”；
- 冲突处理入口。

Windows 客户端在应用启动、恢复前台和用户手动操作时同步；保持运行且会话在线时可以响应主机的同步通知。

### 14.3 Android 客户端

- “扫描二维码连接”；
- 当前主机和连接方式；
- 最后成功同步时间；
- 本地待上传与待下载数量；
- “立即同步”；
- “解除连接”；
- 冲突处理入口。

自动同步严格限制为应用冷启动和从后台回到前台。一次生命周期内需要去重，避免页面切换导致重复同步。

### 14.4 状态反馈

- 同步期间不阻塞查看和编辑本地任务。
- 同一设备只允许一个同步任务运行；重复点击复用当前任务。
- 成功时显示本次上传、下载、合并和冲突数量。
- 失败时保留本地变更并允许重试。
- 有未处理冲突时不能只显示绿色“已同步”。

```dart
abstract interface class SyncTransport {
  Future<SyncSession> connect(SyncEndpoint endpoint);
  Future<void> close();
}

abstract interface class SyncRepository {
  Future<SyncBatch> changesAfter(SyncCursor cursor);
  Future<ApplySyncResult> applyRemoteBatch(SyncBatch batch);
  Future<void> acknowledge(SyncCursor cursor);
}

  Future<DeviceIdentity?> read();
  Future<void> write(DeviceIdentity identity);
  Future<void> clear();
```

WebDAV 等未来实现只能新增 `SyncTransport`，不能绕过同步合并、身份和冲突层。

## 17. 测试矩阵

### 17.1 数据正确性

- 新增、编辑、完成、恢复、删除和跨日移动。
- 分类与标签新增、修改、删除和重新关联。
- 重复任务系列、单次例外和本次及之后修改。
- 手动排序和默认排序切换。
- 双端同时编辑同一任务的不同字段组。
- 双端同时编辑同一字段组。
- 删除与编辑并发。
- 恢复备份后向同步组传播变化。
- 客户端长时间离线后的增量追赶。
- 设备撤销后的墓碑压缩。

### 17.2 网络与生命周期

- 局域网自动发现与手动地址。
- Tailscale IP 与 MagicDNS。
- 主机端口占用和防火墙阻止。
- 同步中途断网、应用退出和 PC 休眠。
- Android 冷启动、前后台切换和快速重复切换。
- 主机在线但客户端应用关闭。
- 多个客户端同时连接主机。
- 主机地址变化后的重新发现。

### 17.3 安全

- 过期或重复使用配对令牌。
- 错误公钥指纹与中间人连接。
- 已撤销设备重新连接。
- 未知协议版本、实体类型和字段。
- 超大、压缩炸弹、深层 JSON 与无效 UTF-8。
- 重放 `operationId` 和倒退游标。
- 日志、备份和发布包敏感信息扫描。

### 17.4 性能目标

- 10,000 条任务的首次局域网同步在代表性设备上可接受，并显示进度。
- 100 条以内的普通增量在稳定局域网中目标为 2 秒内完成。
- 增量同步内存峰值不随完整数据库线性复制多份。
- 日志压缩和清理不能阻塞日历首屏。

具体阈值在 S0 建立基准后冻结，不通过删除测试来降低门槛。

## 18. 发布与兼容策略

- 同步协议版本与应用版本分离。
- 同一主版本内允许旧客户端读取兼容响应，但不允许旧客户端写入自己无法理解的新字段。
- 需要破坏性协议升级时，主机先升级并进入兼容窗口，再提示客户端升级。
- 数据库迁移失败时保持旧数据库和安全备份，不启动同步主机。
- v0.1.0 的 JSON 备份必须能导入 V1.0.1。
- V1.0.1 导出的备份需要明确记录同步元数据是否被排除；设备身份和密钥始终排除。
- Android 正式 APK 必须继续使用现有正式签名密钥。

## 19. 主要风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 把完整备份误当作同步 | 覆盖、重复或丢失修改 | 独立增量日志和冲突引擎 |
| 设备时间不一致 | 新数据被旧数据覆盖 | 混合逻辑时钟 |
| 删除在离线设备复活 | 已删除任务重新出现 | 墓碑、确认游标和设备撤销 |
| Android 后台受限 | 主机无法即时通知手机 | 只承诺启动/回前台/手动同步 |
| Tailscale 地址不可达 | 异地同步失败 | 显示接口、手动地址、可诊断错误 |
| 主机直接暴露公网 | 用户数据和桌面安全风险 | TLS、设备认证、不自动映射公网端口 |
| 设置跨端覆盖 | PC/Android 布局互相破坏 | V1 不同步 settings |
| 自动备份持续堆积 | 占满磁盘 | 自定义目录、每日限频和保留策略 |
| 主机损坏或遗失 | 同步组无法继续协调 | 每端完整本地副本、JSON 备份、重新建组 |

## 20. 最终验收定义

V1.0.1 必须同时满足；第 1～3 项中缺少实体多 PC 的部分按 2026-09-09 项目方决定暂时放弃测试，并作为已知发布豁免保留：

1. 一台 Windows 主机可以和至少一台 Windows 客户端及一台 Android 客户端配对。
2. 局域网和 Tailscale 两种连接均通过真实设备验证。
3. 三台设备离线修改后能够确定性收敛，重复同步不再产生新变化。
4. 删除、完成、排序、标签和重复任务不会在同步后丢失或复活。
5. 所有冲突有记录、有提示、可恢复。
6. 主机或网络不可用时，各客户端仍可完整使用本地 TODO。
7. Android 不常驻后台；打开、回前台和手动操作可以可靠触发同步。
8. 主机能够管理设备备注、撤销设备并主动同步所有在线设备。
9. 用户可以把自动备份放到非系统盘，并限制自动备份数量。
10. 旧数据库和 v0.1.0 JSON 备份可以安全迁移。
11. 发布包不包含用户数据、设备私钥、令牌或开发机配置。
12. Windows、Android、隐私和发布文档更新完成。

满足全部非豁免条件后关闭同步开发阶段，并发布 **EchoDay V1.0.1**。
